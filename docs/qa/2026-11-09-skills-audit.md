## 结论与范围

当前引擎可以承载大多数常规武将技能：摸弃牌、伤害与回复、标记、判定、拼点、转化、技能获得/失去、阶段跳过、额外回合均有现成入口。问题主要是技能本身尚未写完、玩家选择没有传到 AI，或部分规则被简化。不能把“模块成功加载”当作“技能完整可用”。

本轮完成研究资料整理、源码可实现性核查和现状验证，不修改武将技能业务逻辑。只考虑正常串行对局，不为复杂并发、罕见交互、强安全或强稳定性增加工程要求。

范围是**本仓库收录的全部武将档案**，不是外部游戏持续更新的全部武将。规则依据本地研究页和当前源码；没有联网复核不同产品版本的最新技能文本。同名技能在标准、界、SP、国战等版本间不一定相同，不能仅凭同名模块已注册就认为对应档案已实装。

## 主代理对实现方式的判断

| 机制 | 判断 | 当前可复用依据与注意点 |
|---|---|---|
| 摸牌、弃牌、获得/交给牌、伤害、回复、体力上限 | 可直接组合 | `src/engine/atoms/` 与伤害流程；补技能条件和选择即可 |
| 触发技、锁定技、限定/觉醒、计数标记、转换技 | 可实现，通常仅需技能状态 | before/after hooks、`vars`、`marks`、once-per-turn；转换状态要同时投影给AI |
| 判定、改判、拼点 | 可复用现有流程 | `flows/judge.ts`、`flows/rank.ts`；不需另造并发系统 |
| 视为使用、手牌转化、声明普通锦囊 | 可实现 | 影子牌、preceding action、`skills/cards/`；要沿用实际产出牌的目标与响应流程，蛊惑还需要扣牌不提前公开 |
| 获得/失去技能、觉醒授技 | 可实现，先补齐衍生模块 | `添加技能`/`移除技能` 和 `skills/lifecycle.ts` 已存在；“获得技能”本身不是必须扩展引擎的理由 |
| 看顶牌、公开亮牌、分配、选部分牌 | 可复用现有询问与牌区机制 | `ActionPrompt`、`distribute`、card candidates、`整理牌堆`；需分别保留公开与私有信息，以及选择数量/顺序 |
| 跳过阶段、额外回合 | 已有普通路径，按技能接入 | `rules/skip-phase.ts`、`flows/turn.ts`、放权/博图等现有技能；不因“额外回合”四字就判为新框架 |
| 双翻面复正、场上牌移至正确场区 | 可实现，但先纠正现有共享语义 | 当前翻面helper是置背面，巧变是转手牌；不能把现有简化直接复制给更多技能 |
| 对指定目标不限次数、额外目标、不可响应 | 可实现，需补齐服务端与AI共同规则 | 当前次数接口主要按玩家/牌判断；要增加目标上下文，避免界陷阵那样全局放开 |
| 晋势力、隐匿/明置等 | 可实现，需明确新增状态及开局语义 | 当前 `Faction` 只有魏蜀吴群；不能只添武将资料就当晋将已接入 |
| 神典韦的第二武器栏、武将牌作为武器 | 需要扩展装备模型 | 当前 `equipment` 每种槽位只有一个牌ID；需要多槽位、动态武器牌和技能生命周期；属于明确的大项 |
| 国战主副将、半阴阳鱼、队列/阵法、军令 | 需要独立模式支持 | 当前 `GameMode` 只有身份局/1v1，玩家是单武将；普通身份局不能原样承载这些技能。普通技能部分可复用，模式条件不能静默删除 |
| 宝梳、舆、锻造等专属牌 | 需要补具体牌定义与生命周期 | `EquipSlot` 已包含宝物，不必重做宝物槽；仍需牌数据、效果和离场销毁逻辑 |
| 冰【杀】等新增牌/伤害规则 | 需要补相应规则与投影 | 当前 `DamageType` 只有普通、火焰、雷电；晋张春华的清冷等不能只复用现有火/雷杀并换名字 |

上表是实现路径判断，不是工时承诺。对已取得规则并核查的机制，没有发现语言或串行引擎架构使之原则上无法实现；需要模式扩展的条目应单独成批，不能算进“仅补一个技能文件”的工作量。研究页还引用一些未展开的衍生技；缺少规则的衍生技只能记为“规则待补”，不能据父技能文本直接判定完整可实现性。完整引用及本地可补全情况见全量清单。

## 已核实的普通路径缺口与建议顺序

优先级按对 AI 普通操作与规则结果的影响划分，不是安全风险等级。

| 优先级 | 武将/技能 | 当前问题与证据 | 正常实现方式 |
|---|---|---|---|
| P1 | 张角/界张角：黄天、界黄天 | 后端把交牌动作注册在群势力盟友；客户端只在技能所属者注册动作。按真实客户端注册方式，持闪的群角色自己的出牌阶段只枚举到结束阶段，没有交牌动作。见定向探针 | 把盟友可用的共享主动能力加入该座次动作枚举，按主公、势力及回合条件过滤 |
| P1 | 周瑜：反间 | `反间/选花色` 后端要求 `params.suit`；Headless 没有 `chooseSuit` 分支，复现只得到“无牌可出，跳过” | 对四种允许花色生成明确回应动作，提交 `suit` |
| P1 | 毌丘俭：鸿举→清侧 | `鸿举.ts` 授予清侧，但清侧没有模块/注册；觉醒后只有技能名。换荣分支还直接移去旧荣标记、弃置新手牌，没有把换出的旧荣交回手牌，且固定取前k张 | 补清侧；为荣保留真实牌归属并支持选择旧荣，与选中手牌实际交换 |
| P1 | 陆抗：破势→怀柔 | `破势.ts` 失去决堰后添加怀柔，后者没有模块/注册 | 补怀柔的装备重铸动作和AI入口，完成授技后的正常出牌路径 |
| P1 | 界刘禅：界若愚→思蜀 | `界若愚.ts` 只授予激将，源码明确省略思蜀，当前注册表也没有思蜀 | 按选定版本规则补思蜀及准备阶段目标选择 |
| P1 | 于吉/界于吉：蛊惑 | 主动声明仅杀/桃/酒，另有闪和求桃入口；普通锦囊未实现。未经质疑的杀结算仍沿用扣牌ID，影子ID又包含原ID。标准与界版规则文本也有版本口径差异 | 先固定两版规则，再接入普通锦囊声明及对应响应；公开事件使用声明身份，保留实际扣牌供质疑结算 |
| P2 | 张郃/界张郃：巧变/界巧变 | `moveFieldCard()` 装备和延时锦囊最终进入目标手牌，而非目标对应场区；与“将场上一张牌移到另一角色场上”不同 | 按装备/判定区分别移动并验证目标位置，沿用装备加载和延时锦囊流程 |
| P2 | 曹丕/界曹丕：放逐/界放逐等翻面技 | `flows/face-down.ts` 的 `flipFaceDown()` 仅加标签，再次翻面不会复正；多个来源翻面还会叠标签 | 将“翻面一次”的状态切换与“设为背面”分开，在普通技能中使用前者 |
| P2 | 界高顺：界陷阵 | 赢拼点后按全局无限杀放行，扩展到无关目标；普通锦囊额外指定该目标的部分也未完整落实 | 按实际目标判断次数豁免及额外目标，服务端校验、前端与AI候选使用同一语义 |
| P2 | 界曹植：界落英 | “任意张”被实现为全得/全不得；获得后相关牌的后续使用限制也不能仅凭注释认为完整 | 以候选牌集合做0..N选择；按最终规则确认后续效果并保存必要状态 |
| P2 | 界左慈：化身 | 换掉至多两张化身简化成从池尾移除、固定保留展示牌，玩家/AI不能选择具体牌 | 发出可序列化的化身候选和选择结果，按所选ID更换 |

普通使用前应先处理 P1 的入口与衍生技，再集中修正 P2 的规则简化，最后按全量清单扩展未实装武将。这样一批完成后统一跑普通对局和技能测试即可，不需要为每个小变化增加防御框架。

## 验证记录与局限

1. `pnpm exec tsx scripts/audit-skill-runtime.ts`：165将、282静态武将技能、313注册模块；模块加载、createSkill、onInit、onMount **0错误**。319条客户端动作声明都能在某个座次找到后端入口；黄天两条在声明座次没有对应入口，转而在盟友座次存在。这是接线核查，不验证发动后的效果。
2. `pnpm exec tsx scripts/audit-skill-ai-paths.ts`：复现黄天/界黄天盟友无动作、反间无花色选择。该脚本构造正常局面及询问投影，直接调用真实注册和枚举代码；不连接远程模型、不把这些缺口伪装成测试通过。结果见 [AI路径记录](./2026-11-09-skills-ai-paths.json)。
3. `pnpm test:all --reporter=json --outputFile=docs/qa/2026-11-09-skills-tests.json`：**457个测试文件通过，4130条测试通过，0失败，7跳过**。原始报告已压缩成保留计数和跳过条目的[结果摘要](./2026-11-09-skills-tests.json)，7条跳过的是依赖运行中服务的Headless/选将集成项。
4. `pnpm typecheck`：通过。审计脚本另以 `tsx` 实际执行；仓库 eslint 默认忽略 scripts，不能称脚本经过lint验收。
5. 不需要实际模型即可复现上述客户端与规则缺口，故本轮没有调用Gemini/DeepSeek API。全测通过也不意味着所有689个研究档案都能参战，或1361条规则均已验收。
